# Decision log

One row per important decision (scope, data, stack, method…). When a decision changes, a new row
replaces it; old rows are not deleted.

| # | Date | Decision | Why | Alternatives rejected | Who |
|---|---|---|---|---|---|
| 001 | 2026-11-13 | Initial repository structure | So the team could start in an orderly way | — | Pablo |
| 002 | 2026-11-14 | Pre-computed card index (`app/data/`) + live maps and imagery; the app computes the matches in the browser. **Applied.** | The raw data do not change: they are processed once. Calling the APIs on every click would take minutes, need passwords and depend on NASA servers being up during the demo | Calling the APIs on each query | Marc |
| 003 | 2026-11-14 | Compare in physical units with a tolerance, not with percentiles per body. **Applied**, with a soft note instead of the linear one (`docs/09_selection_criteria.md`) | Percentiles would pair "what is typical on Mars" with "what is typical on Earth" (`docs/03_approach.md` §2.1) | Percentiles / z-score per body; a trained AI model (there are no labelled examples) | Marc |
| 004 | 2026-11-14 | The app is organised by "what do you want to test?" (`configs/pruebas.yaml`) + reverse direction + validity of the test. **Applied** (Test menu, any body against any other, Rover test planner) | It is how an engineer tests (by subsystem) and answers the challenge's *"connect your analog to exploration"* | Generic mission profiles | Marc |
| 005 | 2026-11-14 | Repository reorganisation: numbered docs in reading order, `data/external` → `data/catalogs`, `outputs/results` → `app/data`, `mission_profiles.yaml` → `variables.yaml` + `pruebas.yaml` | So everyone knows where each thing goes | — | Marc |
| 006 | 2026-11-14 | Two separate resolutions. **Imagery** (what you see when zooming): as fine as possible (CTX ~5 m on Mars, Sentinel-2 ~10 m on Earth). **Data** (what the similarity index is computed from): moderate but **the same on every body**, at the ~10 km landing-ellipse footprint (MOLA 3.7 km and TES 3 km are fine; GRS ~300 km only gives regional context) | Imagery makes the demo; the index is only fair if both sides are measured at the same scale (slope and roughness change with DEM resolution, `docs/03_approach.md` §2.2) | Computing the index at the finest resolution available on each body | Adrià |
| 007 | 2026-11-14 | The main interaction is **click ANY point of the Moon or Mars → the app finds the most similar place on Earth and flies there**, with a **global card grid for Mars and the Moon** (H3 hexagons; Mars res 5 ≈ 9.1 km, Moon res 4 ≈ 12.3 km, Earth res 6 ≈ 6.5 km), **one file per H3 base cell** so the app only downloads the clicked region. Precision is the cell, not the pixel: the scale the data support. **Applied** (extended to any body against any other) | It is what users expect from a 3D globe, makes the demo free-form ("click wherever you want") and reuses what was built (click → lat/lon, fly-to, formula) | Only the 21 catalogue sites as targets: any other click gives no answer | Adrià |
